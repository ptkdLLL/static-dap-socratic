# S1 符号探索实验：增强 S1 注入是否让“找符号”更可靠？

> 脱敏实验记录。对象是一个 Android 漫画阅读器的 pre-EPUB 基线（含初版 PDF 支持），不是具体业务代码发布。
> 实验目标不是评价某个项目，而是回答一个问题：**在 S1（建立全局视野）阶段加一小段符号查询纪律，是否真的改善探索质量？**

## 1. 结论先行

**有改善，但改善集中在“证据纪律”，不是“符号覆盖量”。**

两组 S1 都能独立完成同一套核心探索：扫描/入库、归档抽象、封面、阅读器、页解码、JNI/VFS、翻译影响面。增强注入组多做了三件事：

1. 明确把 `search_graph` 返回值作为唯一 QN 来源，不手写；
2. 明确 `search_code` 的正则模式和 warning 处理；
3. 在干净环境中工作，没有接触参考实现的符号。

但它**没有**让 `trace_path` 覆盖增加，也**没有**触发 cscope/clang AST 复核；因为这次任务的符号都是普通函数/类方法，没有踩到 C++ 嵌套类、重载、条件编译这些长尾缺口。

所以：**S1 这段注入值得保留，但不要据此宣称“符号探索能力大幅提升”；它提升的是可审计性，不是覆盖率。**

## 2. 实验设计

- 项目：Android 漫画阅读器 pre-EPUB 基线，包含初版 PDF 支持，不含 EPUB 源码。
- 任务：同一句用户消息——
  `基于静态工具与dap联合，评估给这个尚未实现 EPUB 的漫画阅读器增加 EPUB 支持。`
- 两组：
  - **Baseline**：原始 S1 注入；
  - **Treatment**：S1 + 一段符号查询纪律（QN 只取工具返回值、调用链用 `trace_path`、`search_code` 正则显式化、C++ 特殊形态用 cscope/clang AST、改后重建索引）。
- 约束：不修改源码；只做 S1；不预先给目标符号清单；两组各自从项目副本开始，自行 `index_repository`。
- 产物：各自的 `PLAN.md` + `REPORT-research.md`。
- 统计：n=1/组，不是统计显著实验；结论只作为方向性证据。

## 3. 结果

| 指标 | Baseline | Treatment |
|---|---|---|
| 索引 | 自行 full 重建 | 自行 full 重建 |
| 节点/边 | 111,560 / 627,019 | 111,560 / 627,259 |
| 工具调用 | 145 | 152 |
| Token | 20.3M | 20.4M |
| 耗时 | 7.5 min | 9.3 min |
| 报告 | 358 行 | 704 行 |
| PLAN | 251 行 | 446 行 |
| `trace_path` | 2 条关键链 | 2 条关键链 |
| 精确 QN | 报告未列表 | 明确“全部取自 search_graph” |
| `search_code` 正则 | 未强调 | `regex=true`，无 warning 零结果 |
| cscope/clang AST | 未使用 | 未使用（判断为普通符号，无歧义） |
| 环境纯净度 | 接触过含参考符号的已装构建 | 使用干净 pre-EPUB 构建 |

## 4. 增强注入带来的实际变化

### 4.1 QN 使用更可审计

Treatment 在报告里明确写了“所有 QN 取自 `search_graph` 返回值，未手写”，并在架构入口使用完整 QN 引用。  
Baseline 也声称没有手写 QN，但报告里没有把这条纪律显式化，读者无法从产物中复核。

### 4.2 零结果更可信

Treatment 明确使用 `search_code(regex=true)`，并检查“无 warning 的零命中”才作为事实。  
Baseline 没有把这个处理写成可复核的步骤；虽然它实际没有遇到假零，但方法论上少了这层保险。

### 4.3 方案分层更细

Treatment 把“EPUB 支持”拆成三种接入面：

- 原生 `EpubArchive`：实现 `IArchive`，复用现有页模型；适合图片型/固定版式；
- Kotlin `EpubBookSource` + 独立阅读屏：适合通用文本 EPUB；
- 只把 `.epub` 加进 zip 白名单：只能算探针，不能叫支持。

它还指出 `open_archive_path` 同时服务阅读、封面、页索引，不能只改阅读器。  
Baseline 也做了 A/B/C 分层，但 Treatment 对“归档接口与页模型边界”讲得更细。

### 4.4 真实样本证据更具体

Treatment 给出四组对比，例如“16 图 vs 13 章”“822 图 vs 481 章”“47 图 vs 89 spine 页”“0 图直接失败”，直接说明“EPUB 当 zip”会怎样失真。  
Baseline 的样本证据是“1/2/0/2 页”，也能说明问题，但 Treatment 的对比更完整。

## 5. 没有改善的部分

1. **`trace_path` 覆盖没有增加**：两组都只对约两条关键链做了调用链核验；多数调用关系仍靠图度数或源码阅读。
2. **C++ 交叉验证没有发生**：注入里写了“嵌套类/重载/宏用 cscope/clang AST 复核”，但这次任务的符号都是普通函数/类方法，条款没有被触发。要验证它，必须换一个会踩 `Outer::Inner::method`、重载或条件编译的任务。
3. **效率没有提升**：Token 基本持平，耗时多 1.8 分钟，报告长度接近翻倍。质量提升是“更细、更可审计”，不是“更省”。
4. **S1 产物偏重**：704 行报告 + 446 行 PLAN 已经接近 S3 的体量，可能压缩后续阶段的独立判断空间。

## 6. 对插件的启示

- **S1 是放符号查询纪律的正确位置**：它是第一次引入静态工具，且指令会留在上下文里；不需要在 S2-S6 重复。
- **不要因为这次结果就继续加注入**：这次只证明“一小段纪律能被加载、能改变报告的证据呈现”，没有证明“更多注入更好”。
- **S5 的“改完重建索引”还没有被这次实验覆盖**：本实验只做 S1；S5 需要另一次完整落码任务验证。
- **要验证 C++ 长尾缺口，必须用会踩缺口的任务**：普通 Android 任务里 codebase_memory 足够强，不能拿它证明嵌套类/重载/条件编译也没问题。

## 7. 静态工具依赖：codebase_memory 不够

这个实验也暴露了一个产品层问题：**只提示 `codebase_memory` MCP 是不够的。**

### 7.1 codebase_memory 的强项

- 全局索引、跨文件符号、调用关系、数据形状；
- 普通函数、类方法、JNI、Kotlin/Java/C++ 混合项目；
- `search_graph` / `get_code_snippet` / `trace_path` 足以完成大多数 S1 探索。

### 7.2 它的 C++ 长尾缺口

- 嵌套类 `Outer::Inner::method` 可能没有 Method 节点；
- 重载方法按 `(project, qualified_name)` 合并，多个重载可能只看到一个；
- 条件编译/多构建配置只索引一个分支，缺少 `compile_commands.json` 时更明显；
- QN 结构不直观，不能靠后缀猜。

这些缺口不意味着工具整体不可用；社区评测里 C++ 仍属于高质量档。但**在 C++ 任务里不能把 codebase_memory 当唯一真相**。

### 7.3 建议的静态工具组合

| 工具 | 角色 | 何时必须 |
|---|---|---|
| `codebase_memory` MCP | 全局图、符号、调用、数据形状 | 所有任务 |
| `cscope` | C/C++ callers/callees/references，含 static 函数 | C/C++ 任务，或图结果可疑时 |
| `clang` / `clang++` | AST dump：函数/变量/类型边界、声明与实现 | C/C++ 任务，或涉及宏/嵌套类/重载时 |
| `SCIP` / Joern / CodeGraph | 补充语义索引 | 可选；不能替代 cscope/AST 的边界核验 |
| DAP MCP | 运行时实际值、线程、分支 | 运行时契约验证 |

最小检查：

```bash
command -v cscope
clang --version
# 以及 codebase_memory MCP 的 index_repository / search_graph 可调用
```

### 7.4 使用原则

```text
graph 先给候选
→ QN 用 search_graph 返回值
→ 普通符号 get_code_snippet/trace_path
→ C++ 嵌套类/重载/宏/条件编译用 cscope + clang AST 复核
→ 运行时用 DAP/探针/日志
```

**cscope/clang AST 不是 codebase_memory 的替代品，而是 C++ 长尾缺口的补盲。** 只装 codebase_memory，普通任务够用；C++ 复杂符号任务会在最需要精确性的地方缺少交叉验证。

## 8. 复现边界

- 两组各 n=1，不能做统计显著性结论；
- Baseline 组接触过含参考符号的已装构建，Treatment 使用干净 pre-EPUB 构建；环境差异会放大“纯净度”差异，不能全部归因于注入；
- 本实验只评 S1，不评 S2-S6，也不评 S5 的索引重建条款；
- 任务没有踩 C++ 嵌套类/重载/条件编译，因此 cscope/clang AST 条款没有被真正测试。

## 9. 一句话

**S1 的这段注入值得保留：它让符号证据更可审计、零结果更可信、方案分层更细；但它没有让符号覆盖和调用链验证自动变强。要继续验证 C++ 长尾缺口，需要专门构造会踩嵌套类/重载/条件编译的任务，并把 cscope + clang AST 作为首页明示的静态工具依赖。**
