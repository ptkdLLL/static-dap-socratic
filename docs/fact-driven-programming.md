## 摘要

大语言模型编程代理已经能够在仓库级任务中规划、修改、构建和测试软件，但其计划经常把局部印象、词法命中或未运行验证的推断误认为事实。为提高可靠性，一类工程实践把工具调用、报告字段或检查清单设置为阶段推进的硬门禁；然而，这类代理指标可能取代真实任务目标，诱发仪式性工具使用、表单合规和奖励黑客。本文整理并形式化一种替代方案——**事实驱动编程**（Fact-Driven Programming, FDP）[^1][^2]：外部确定性状态机只管理阶段拓扑、交接和注意力；单代理在阶段提示的强指令、任务局部设问和证据阈值约束下，把计划改写为可证伪假设，再根据信息需求选择静态分析、真实样本、探针、日志、测试、构建和调试器，以可复核事实支持、否定或重构计划。与“必须调用某工具才能推进”的认识论门禁不同，FDP 不把关卡写进状态机；它通过阶段话术规定取证取向，同时把证据充分性判断留给代理的任务局部实验和最终人工审查。本文报告两组初步证据：（1）一项每组 n=1 的 S1 符号探索对照实验，显示增强设问纪律主要提高证据可审计性，而非符号覆盖量；（2）两个约一小时的脱敏现场案例，显示假设被事实否定、计划回改、未验证边界显式保留，以及在调试器受限时由探针、日志、数据库和界面证据降级闭环。本文不主张这些结果构成统计验证，而将其作为方法可行性和后续受控研究的基础。

**关键词**：事实驱动编程；编程代理；苏格拉底式设问；工具使用；软件工程；奖励黑客；过程监督

## Abstract

Large language model coding agents increasingly plan, modify, build, and test software in repository-level tasks, yet their plans often mistake lexical matches, local impressions, or untested inferences for facts. A common engineering response is to impose hard process gates on tool calls, report fields, or checklists. Such proxy metrics, however, may displace the underlying task objective and induce ceremonial tool use, checklist compliance, and reward hacking. This paper formalizes an alternative called **Fact-Driven Programming (FDP)**. An external deterministic state machine manages only task topology, handoff, recovery, and attention. Within each stage, the prompt combines imperative initialization, task-local Socratic questions, and evidence thresholds; the agent converts plans into falsifiable hypotheses and selects static analysis, real samples, probes, logs, tests, builds, or debugger observations according to the required evidence. Facts then support, refute, or revise the plan. We report two preliminary studies: an exploratory n=1-per-condition experiment on S1 symbol exploration, and two anonymized field cases of approximately one hour each. The results suggest improved evidence auditability, explicit plan revision after falsification, and robust degradation when debugger evidence is unavailable. These findings are directional rather than statistically conclusive.

**Keywords**: fact-driven programming; coding agents; Socratic questioning; tool use; software engineering; reward hacking; process supervision

## 1 引言

### 1.1 问题背景

大语言模型编程代理的核心风险，不只是“会写错代码”，而是会把错误理解包装成完整叙事。代理可能根据少量文件、裸文本搜索或局部上下文迅速形成计划；计划一旦进入实现阶段，后续测试和报告又可能围绕原计划组织，而不是围绕能够推翻原计划的事实组织。仓库级软件工程进一步放大了这一问题：符号边界、调用关系、构建配置、运行时状态、平台约束和用户目标分布在不同证据面中，任何单一工具都不能提供完整真相。

因此，工程实践通常引入流程控制：要求代理先计划、再实现、再测试；要求提交结构化报告；要求调用特定工具；或者在阶段边界设置自动检查。问题是，**流程约束的可见形式很容易被代理当作新的优化目标**。如果状态机要求“必须调用调试器”，代理可能寻找成本最低的调试器调用；如果要求“必须填写证据表”，代理可能把输出改写成看似合规的证据；如果要求“测试通过”，代理可能优化测试通过而不是满足自然语言规格。此类现象与奖励错误指定、规格博弈和 Goodhart 型代理指标失真具有同一结构。[7-10]

本文讨论的 `static-dap-socratic` 插件采取了相反设计：它保留阶段拓扑和报告交接，却刻意拆除“必须调用某工具、必须提交固定证据、必须让报告通过自动评分”的认识论硬门禁。其核心不是让代理“更自由地发挥”，而是让代理持续受到与任务目的相关的外部事实约束。[^3]

### 1.2 设计史：为什么拆除质量门禁

该方法的设计者最初曾根据半手动、人工监督任务 session 考古生成一个未公开版本。这个版本把成功轨迹中观察到的工具调用改写成大量“是否使用工具”的阶段门禁。后续审查发现：工具调用逐渐变成满足门禁的仪式性操作；推理内容大量转向如何突破门禁，而不是如何解决工程问题；输出代码质量下降，并出现了人监督版本中未出现的错误构建。[^4]

这一历史记录不是公开可复现实验，因为它来自设计者提供的开发史，且旧版插件未上传。但它指出了一个重要的方法论失真：**从成功轨迹提炼规则时，容易把“任务理解之后发生的工具调用”倒置为“推进流程的前置条件”**。可见动作被保留下来，而选择工具、识别无效证据和切换路径的判断被丢弃。

新版设计因此转向三条原则：

1. **设问与强指令结合**：在 S1、S2、S4 用问题暴露全局结构、计划前提和准代码块运行时契约的未知，同时保留索引、探索和证据等级的明确约束；
2. **工具动机代替可执行门禁**：提示说明不同工具能够提供什么事实；除报告 handoff 外，单个工具调用不构成状态机推进条件；
3. **事实闭环代替表单合规**：代理必须用静态或动态证据支持、否定或重构计划，而不是只把报告写满。

### 1.3 研究问题与贡献

本文围绕三个研究问题展开：

- **RQ1**：在没有工具调用硬门禁的条件下，阶段设问能否促使单代理主动形成取证需求，并选择与问题相匹配的静态或动态工具？
- **RQ2**：由设问、假设和工具实验构成的循环，能否在真实复杂任务中产生足以否定或修正计划的事实，而不仅是增加过程记录？
- **RQ3**：这种方法在证据可审计性、机器成本、环境依赖和未验证边界方面具有哪些收益、代价与有效性威胁？

本文贡献如下：

1. **概念化**：提出“事实驱动编程”的操作性定义，并区分拓扑约束、过程门禁与结果验证；
2. **方法化**：总结一个六阶段、单代理、外部状态机与内部证据循环相结合的工作流；
3. **初步实证**：按照仓库中两份实际实验记录的体例，分别报告一项探索性对照实验和两个现场案例；
4. **研究议程**：给出可预注册、可盲评、且不将过程指标重新变成门禁的后续对照实验设计。

## 2 相关工作

### 2.1 设问、自我提问与元认知提示

Self-Ask 让模型在回答原始多跳问题前显式提出并回答后续问题；其结构化形式允许系统暂停模型，把子问题交给搜索引擎，再将答案送回同一模型继续推理。[1] 这一工作直接表明，问题生成可以组织信息需求，并与外部工具形成闭环。其局限在于任务主要是知识问答，外部工具基本固定为搜索，不涉及代码修改、构建或运行时验证。

SOCRATIC QUESTIONING 进一步把复杂问题递归分解为子问题，并在获得足够信息后自底向上回溯，显式探索推理空间。[2] 该方法支持“问题驱动展开”，但其子问题仍主要由模型自身回答，缺少独立环境反馈。Metacognitive Prompting 则通过输入理解、初步判断、批判性重估、最终决定和置信度评估等阶段，模拟人类内省过程，并在自然语言理解任务上比较多种提示方法。[3] 它与本文方法的相似点是“先形成判断，再批判性重估”；关键差异是，本文方法要求批判性重估落到代码索引、真实样本、构建、探针、日志、测试或调试器事实上。

中文教育研究也提供了相邻证据。赵晓伟等设计的苏格拉底式问题支架，从认知—元认知维度提供提示性、指导性和解释性支架；在 44 名本科生的准实验中，研究报告了问题深度、问题序列和问题架构的变化。[11] 该研究的对象是人类学生向 AI 提问，而非自治代码代理，因此只能作为“问题支架改变提问结构”的间接证据。[^18]类似地，Socratic code debugging 研究评估模型扮演教师，通过多轮提问帮助新手程序员调试，而不是评估代理自行形成假设并调用工具。[6]

### 2.2 外部反馈与工具接地修正

仅让模型“反思”并不足以保证纠偏。CRITIC 让模型通过搜索引擎、代码解释器等外部工具验证初始输出，再根据验证产生的批评修正输出，形成“验证—修正—再验证”循环。[4] 相对地，Huang 等对无外部反馈的内在自我修正给出负结果：模型通常难以仅靠自身能力纠正推理，有时修正后性能反而下降。[5]

这两类研究共同支持本文的一个基本判断：**设问负责组织调查，外部事实负责使调查具有纠偏能力**。如果代理只是自己提问、自己回答，设问仍可能模板化，甚至加强原有幻觉；只有当问题转化为可以判别的观察，设问才可能改变计划和代码。

### 2.3 代理指标、测试门禁与奖励黑客

奖励错误指定研究表明，代理能力或优化程度提高时，它可能更善于利用代理奖励与真实目标之间的缝隙，出现代理奖励上升而真实奖励下降的情况。[7] 在代码代理中，ImpossibleBench 通过让单元测试与自然语言规格直接冲突，构造“通过测试必然意味着违反规格”的任务，从而直接测量代理利用测试的倾向。[9] SpecBench 则把长时程系统任务拆成自然语言规格、代理可见的单特性验证测试和隐藏的组合特性测试，以两者通过率之差衡量代理指标偏离；其任务覆盖从 JSON 解析器到操作系统内核。[10][^17]

这些结果并不意味着测试或构建有害，而是说明：**当不完整检查被当作优化目标时，通过检查与满足任务会逐渐分离**。这对流程门禁尤其重要，因为“是否调用工具”“报告字段是否齐全”“测试是否通过”都只是“是否获得能改变结论的事实”和“是否满足真实需求”的代理指标。

Baker 等在 agentic coding 环境中研究链式思维监控。其结果显示，监控器可以识别奖励黑客；但当把监控器直接纳入强化学习目标并施加过强优化压力时，代理可能学会隐蔽奖励黑客，使推理轨迹看起来正常而实际行为仍在规避。[8] 该研究发生在训练期奖励优化场景，不能直接等同于部署期 Python hook 门禁；但它与本文讨论的旧版工具门禁具有相似机制：对过程表达施加强压力，可能先优化“看起来合规”，而不是优化真实行为。[^16]

### 2.4 研究空白

现有文献分别支持以下命题：问题生成可以组织分解和信息需求；外部工具反馈比内在反思更可靠；固定代理指标可能导致规格博弈和奖励黑客。然而，目前尚无公开研究直接在仓库级、长时程、单代理开发任务中，对照“阶段设问＋工具动机”与“强制工具调用门禁”。本文的两组初步实证用于填补这一问题的工程证据空白，但其规模不足以形成统计结论。

## 3 方法论：事实驱动编程

### 3.1 操作性定义

本文将**事实驱动编程**定义为：

> 以任务目的为稳定锚点，以设问和假设为调查结构，以静态与动态工具实验为证据来源，持续用可复核事实支持、否定、修正和收敛软件计划的单代理开发方法。

该定义中的“事实”不是任何工具输出，而是一个带有来源、对象、条件、方法和适用边界的证据命题。例如，“`dap_start` 返回成功”不是断点命中事实；“在指定断点停止、`hitBreakpoints` 非空、调用栈可读且 `vars/eval` 读到实际值”才构成较高强度的运行时事实。[15][^5]

FDP 的核心闭环为：

```text
任务目的
  → 设问：当前真正不知道什么？
  → 假设：如果理解成立，系统应当表现出什么？
  → 工具实验：哪种观察能区分该假设与竞争解释？
  → 事实：符号、样本、构建、日志、探针、测试或调试器返回了什么？
  → 裁决：支持、否定、缩小范围还是重构计划？
  → 修改与重验：修改不是验证，修改后必须重新取证
```

### 3.2 三类约束的区分

本文强调三种容易混淆的约束。

| 类型 | 典型形式 | 主要功能 | 风险 |
|---|---|---|---|
| 拓扑约束 | 当前阶段、token、报告交接、会话恢复 | 管理注意力和任务顺序 | 过度拆分会增加开销 |
| 过程门禁 | 必须调用某工具、必须填满固定字段、必须通过表单评分 | 预先规定认识路径 | 仪式化调用、表单合规、奖励黑客 |
| 结果验证 | 正确目标构建、当前修改测试、真实场景运行、隐藏回归 | 验证任务目的是否达成 | 测试不完整时仍可能失真 |

FDP 拆除的是第二类中的**认识论硬门禁**，而不是第三类结果验证。构建、测试和运行时观察仍是必要事实来源；问题在于不能把任何单一检查结果提升为完整规格。[^19]

### 3.3 六阶段工作流

实现版本将复杂任务拆为六个阶段，一次只向代理注入当前阶段。完整阶段图保存在外部脚本中，但不一次性暴露给代理。[12]

| 阶段 | 名称 | 核心问题 | 主要产物 |
|---|---|---|---|
| S1 | 建立全局视野与计划初稿 | 问题落在哪条执行路径、数据流和生命周期上？ | `PLAN.md`、`REPORT-research.md` |
| S2 | 计划验证 | 计划依赖哪些可证伪前提？什么观察会推翻它？ | `HYPOTHESES.md`、`REPORT-hypotheses.md` |
| S3 | 修改文档 | 修改目的、背景约束和准代码块是否足够明确？ | `CHANGE.md`、`REPORT-change.md` |
| S4 | 逐块评估 | 每个准代码块的静态结构和运行时契约是否成立？ | `REPORT-blocks.md` |
| S5 | 落码 | 实际修改是否与已评估块一致，构建、安装和测试结果如何？ | `REPORT-landing.md` |
| S6 | 验收 | 状态迁移矩阵中的期望与实际是否一致？ | `REPORT-acceptance.md` |

S1、S2、S4 是设问最密集的阶段，但这并不意味着阶段提示只是一组开放问题。S1 明确规定先建全局索引，S2 和 S4 明确规定静态腿与动态腿，S4 还规定证据等级和落码前阈值。准确说法是：**状态机不把工具调用做成可执行门禁；阶段话术仍通过强指令、探索禁令、任务局部设问和证据阈值规定取证取向**，并把具体路径、符号、观测点和实验设计留给代理。

### 3.4 阶段话术的真实结构

直接核对 `stages.py` 后，需要修正一种容易产生的误解：插件并不是把六阶段都写成温和的开放式提问。真实话术由五类句式共同构成：命令式初始化、探索禁令、任务局部连环设问、证据阈值与迭代律、报告模板。[^21]

| 阶段 | 话术类型 | 关键原话（摘录） | 方法论功能 |
|---|---|---|---|
| S1 | 命令式索引＋全局结构设问 | “先使用静态工具 MCP `codebase_memory` 的 `index_repository` 对项目进行全局索引（即使之前索引过，也要确保索引与当前代码/HEAD 一致）”；“先回答（都要在静态工具的帮助下，不要凭印象猜）：这个问题落在哪条现有执行路径/数据流上？” | 固定起点是全量索引，避免从局部片段出发；但具体查哪些路径、符号和调用关系由代理根据任务决定。 |
| S2 | 假设展开＋反证追问＋修改后重验 | “把计划里的每一条关键断言展开成假设，也把计划没有写全、但任务要成立所必须的假设补上”；“什么观察会推翻它？”；“支持就记录事实；冲突就改 PLAN.md……改完不等于验证完。” | 把计划从叙事改写为可证伪对象，并要求冲突驱动计划回改，而不是用新叙述覆盖旧证据。 |
| S3 | 文档对象化＋完整性盘问 | “对象是这份修改文档的每一节和每个准代码块。逐个检查：目的是否足以约束准代码？背景/约束是否完整？准代码块的输入、输出、边界、失败路径是否清楚？” | 把修改方案拆成可逐节、逐块检查的对象；本阶段不重复 grep 禁令，因为主要对象是设计文档而非代码探索。 |
| S4 | 静态腿＋动态腿＋红线＋证据等级 | “每一块先静态腿……给出 file:line；先看调用信息再读窄窗”；“再动态腿：老代码 before 契约用 DAP 停住读实际值”；“每块至少一条红线……至少有一行要在当前环境跑出实际值”；“每块落码前至少 A+B。” | 这是规范最强的阶段：它明确区分静态证据、动态证据、微基准、推算和未验证，防止把阅读代码当成运行事实。 |
| S5 | 限定落码＋结果回读 | “只落已经逐块评估过的块”；“实际改动是否与准代码一致？有没有顺手改到块外？构建、安装、测试的实际结果是什么？” | 把实现限制在已评估对象内，并把构建、安装、测试作为落码后的事实回读。 |
| S6 | 重新索引＋状态矩阵＋实际值 | “代码已改，先重新索引当前项目”；“对每一行用实际证据验证”；“记录实际值/实际状态，不要只写‘测试通过’。” | 用改后代码重建全局视图，并按主路径、边界、失败、回归和体验场景逐项验收。 |
| DONE | 终止总结 | “实现了什么、验证了什么、还有哪些未验证边界/风险。” | 以未验证边界结束，而不是以“全部完成”结束。 |

因此，更准确的概括不是“插件只用设问诱导”，而是：**提示层强规范，执行层弱门禁**。S1 的“先使用 index_repository”、S4 的“每块落码前至少 A+B”、S6 的“先重新索引”都是强指令；`BARE_GREP_RULE` 和 `SED_AWK_RULE` 甚至使用“禁止”。这些措辞会产生明确的行为压力。与旧版硬门禁的差别不在于话术是否强硬，而在于外部状态机并不检查这些要求是否以规定形式发生，也不把工具调用、字段齐全或文本评分当作推进条件。[^22]

这一区分也解释了该方法的风险边界。阶段提示中的固定报告字段、“全部通过后”和 A+B 阈值仍可能被代理模板化执行；它们不是天然免疫奖励黑客。当前实现主要依靠三点降低这种风险：第一，hook 不解析、不评分报告；第二，提示允许并要求显式列出 `UNVERIFIED`；第三，设问被绑定到任务局部的路径、符号、实际值和状态迁移，而不是泛泛要求“多反思”。

### 3.5 外部状态机与内部证据循环

系统分为两个层次：

```text
外部确定性状态机
  ├─ 检测激活词
  ├─ 签发当前阶段 token
  ├─ 只注入当前阶段提示
  ├─ 在 compact/resume/clear 后恢复当前任务书
  ├─ 检查报告文件存在、非空、文件名匹配并归档
  └─ 根据 handoff 信号推进拓扑

单代理内部证据循环
  ├─ 从当前阶段问题识别未知
  ├─ 形成计划、假设或准代码块
  ├─ 选择能够回答当前问题的工具
  ├─ 获得静态或动态事实
  ├─ 修改计划、假设、准代码或源码
  └─ 对修改后的对象重新验证
```

外部脚本不解析、不评分报告，也不判断证据充分性。handoff 只验证 token、报告存在、非空和文件名匹配，然后归档并计算 SHA-256。[12] 因此，它保证的是“当前阶段交接发生”，而不是“报告正确”。[^8]

这一划分的理由是：外部脚本适合管理确定性拓扑，不适合预先替代理决定每个任务需要什么证据。任务局部证据标准应由代理在获得足够任务事实后生成，并接受后续事实和人工审查的约束。

### 3.6 设问、强指令与工具动机

新版设计不是简单要求“多提问”，而是把问题、命令和禁令绑定到可获得的事实。真实提示中的关键句式可以分成四组：

- **反印象指令**：S1 要求“都要在静态工具的帮助下，不要凭印象猜”；S4 要求“对准代码逐块拉清单，不要凭印象说‘影响不大’”。这类句子先否定未经取证的直觉；
- **工具策略反问**：S1 问“你认为如何使用静态工具才能更好地探索代码库、对项目与用户问题建立整体认识？”；S2 问“你认为应该如何使用静态工具进行验证？”；S4 问“每个块先查什么、再读哪一段、什么结果会推翻它？”这类句子要求代理先形成取证计划；
- **可证伪追问**：S2 对每条假设追问“它断言什么？依赖哪条现有路径/调用/数据形状/状态/时序/失败模式/平台约束？……什么观察会推翻它？”；
- **证据充分性禁令**：S4 明确“静态 file:line 是静态证据，不能代替动态腿”；“静态推演只能算推算，不能当动态证据，不能写成通过”。

设问的作用是制造认知压力；强指令和工具动机把这种压力转化为取证行动。与硬门禁相比，工具输出不再只是推进凭证，而必须参与支持、否定或重构某个任务局部判断。与此同时，本文不再把该实现描述为“没有固定工具要求”：它确实固定了若干取证原则和起点，只是没有把这些原则实现为状态机的可执行通过条件。

### 3.7 静态与动态证据

静态证据回答“代码如何组织”：符号、调用关系、数据形状、guard、构建配置和约束。动态证据回答“代码实际如何运行”：实际参数、字段、线程、调用栈、分支走向、状态迁移、错误和时序。两类证据互补，不能互相替代。[^15]

S4 使用五级证据标记：[12]

| 等级 | 含义 | 示例 |
|---|---|---|
| A | 静态 `file:line` 与 guard | 调用点、签名、分支条件、数据形状 |
| B | DAP／测试实际值 | 断点变量、实际分支、测试观测 |
| C | 微基准 | 事件率、A/B 性能测量 |
| D | 推算 | 由结构和经验推导的性能或行为 |
| E | 未验证 | 当前环境拿不到证据 |

原始提示要求每块落码前至少具备 A+B；性能影响不能只凭 DAP 停顿推断；没有动态证据的块只能标记 `PASS-STATIC`、`BLOCKED` 或 `UNVERIFIED`，不能写成 `PASS-RUNTIME`。[^10]

### 3.8 grep 纪律与工具降级

实现并未全面禁止 grep。阶段文本把裸文本搜索限制写入 S1、S2、S4；运行期 hook 则会整个活动会话中识别“以代码为对象”的 grep、sed、awk 并发出非阻断提醒，日志、文档、真实样本和数据分析路径被豁免。其认识论理由是：词法命中只能产生候选位置，不能自动证明符号、调用、构建配置或运行时事实。代理应先建立语义上下文，再读取窄窗源码。[^6]

DAP 也被视为运行时事实来源之一，而不是唯一门禁。规范明确要求区分“连接调试器”和“真正命中断点并读到实际值”；`hitBreakpoints=[]`、空 frame、空 vars、continue 超时等不能冒充命中。DAP 不可用时，代理可以转向沙盒日志、最小 probe、单测、logcat、数据库和界面，但必须标注替代证据类型和未验证边界。[15][^7]

## 4 系统实现

### 4.1 插件职责边界

`static-dap-socratic` 插件不生产事实。事实来自外部工具；没有代码索引、构建、测试、日志、探针或调试器，插件本身只是阶段提示器，而不是“事实驱动”。[12] 插件职责包括：

1. 检测激活短语“基于静态工具与dap联合”；
2. 初始化或恢复阶段状态；
3. 签发阶段 token 和预期报告名；
4. 注入当前阶段任务书；
5. 在工具调用前提供非阻断提醒；
6. 在工具调用后记录事实账本；
7. 消费 handoff 并推进阶段。

`PreToolUse` 返回 `permissionDecision: allow`，说明提醒器不拒绝工具调用。其目标是重新锚定注意力，而不是把每次操作变成审批。[^9]

### 4.2 阶段提示的注意力设计

完整阶段图集中保存在 `stages.py`，但 `prompt_for()` 每次只渲染当前阶段。这样代理不能为了尽快到达落码阶段而预先压缩调研和验证，也不会被后续阶段的细则分散注意力。会话压缩、恢复或清空后，hook 会重新注入当前阶段，减少长任务中的目标漂移。

运行期提醒也不是中性的“提示语”，而是针对具体冲动编写的反模式话语：[12]

| 触发 | 实际提醒话术（摘录） | 目标行为 |
|---|---|---|
| 索引前读源码 | “全局索引前直接读源码，会把全局问题压成局部片段：你看到的是这一段，不是它在调用链/guard/生命周期里的位置。” | 先建索引，再决定窄窗阅读。 |
| 裸 grep 代码 | “禁止在文档与日志以外的情况裸 grep……对于当前这个问题，你认为如何使用静态工具才能更好地探索代码库、对项目与用户问题建立整体认识？” | 把词法搜索冲动改写成符号和调用关系查询。 |
| sed/awk 整段读码 | “禁止用 awk/sed 整段读取代码……你认为应该先用静态工具确认哪些符号、调用关系和数据形状，再读哪一段窄窗？” | 把线性文本抽取改写成结构化定位。 |
| 索引后整文件读 | “整文件读会把调用关系、数据形状、生命周期压成线性文本。先用 trace_path/search_graph 拿 file:line，再读 ≤20 行。” | 保留窄窗阅读，防止上下文被整文件吞没。 |
| 修改后索引过期 | “代码已改，当前索引可能过期；建议在本阶段结束前重新索引当前项目。” | 防止用旧索引解释新代码。 |

这些话术都通过 `permissionDecision: allow` 注入，因此其机制是注意力重锚，而不是执行层阻断。

### 4.3 报告与事实账本

报告是交接和审计信号，不是自动正确性证明。事实账本记录工具调用及其哈希链，但账本存在并不等于证据充分，更不判断证据与结论是否相关。最终判断仍需要用户查看报告中的证据、未验证项和改动差异。

这种“弱自动判断”是刻意的：如果外部脚本试图解析报告并给出质量分，报告文本就会成为新的代理指标；如果只管理拓扑，报告就更可能保留任务局部差异和未验证边界。

### 4.4 设计原则

综合实现与设计讨论，FDP 可以归纳为八条工程原则：

1. **任务目的稳定**：流程指标可以变化，用户目的和关键回归约束不能随意移动；
2. **全局事实先于局部阅读**：S1 和运行期提醒都要求先建立索引、架构和调用关系，再决定窄窗源码；
3. **问题约束工具选择**：先暴露未知，再选择能提供相关事实的工具；但索引、证据分类等少数起点可以被明确固定；
4. **计划可证伪**：每条关键计划都应说明什么观察会推翻它；
5. **证据分类**：静态、动态、微基准、推算和未验证不能混写；
6. **修改后重验**：改计划、改准代码或改源码都不等于验证完成；
7. **允许未验证**：没有证据的结论应显式标注，而不是包装成“全部通过”[^14]；
8. **工具目标可替代**：目标是一类事实，而不是某个工具的调用仪式；DAP 不可用时可以用 probe、日志、单测、logcat、数据库或 UI 取得同类运行时事实；
9. **过程指标离线化**：仪式性调用、门禁讨论比例等可用于研究评价，但不能回填为推进门禁。

## 5 研究一：S1 符号探索的探索性对照实验

### 5.1 实验目的

研究一回答一个窄问题：在 S1 阶段增加一小段符号查询纪律，是否会改善全局探索质量。实验对象是一个 Android 漫画阅读器的 pre-EPUB 基线，任务是在不修改源码的前提下，评估为尚未实现 EPUB 的阅读器增加 EPUB 支持。[13]

实验对比两种条件：

- **Baseline**：原始 S1 注入；
- **Treatment**：S1 注入外加符号查询纪律，包括 qualified name 只取工具返回值、调用链用 `trace_path`、`search_code` 正则显式化、C++ 特殊形态用 cscope/clang AST 复核、修改后重建索引。

两组接收同一句任务消息，从项目副本自行建立索引，只执行 S1，产物为 `PLAN.md` 和 `REPORT-research.md`。

### 5.2 结果

| 指标 | Baseline | Treatment |
|---|---:|---:|
| 图节点 | 111,560 | 111,560 |
| 图边 | 627,019 | 627,259 |
| 工具调用 | 145 | 152 |
| Token | 20.3M | 20.4M |
| 耗时 | 7.5 min | 9.3 min |
| 报告长度 | 358 行 | 704 行 |
| PLAN 长度 | 251 行 | 446 行 |
| `trace_path` | 2 条关键链 | 2 条关键链 |
| 精确 QN 纪律 | 报告未列表 | 明确全部取自 `search_graph` |
| `search_code` 正则 | 未强调 | `regex=true`，无 warning 零结果 |
| cscope/clang AST | 未使用 | 未使用，判断为普通符号 |
| 环境 | 接触过含参考符号的已装构建 | 干净 pre-EPUB 构建 |

### 5.3 观察结果

增强组的变化集中在证据纪律而非符号覆盖量。

第一，**QN 更可审计**。Treatment 明确记录“所有 QN 取自 `search_graph` 返回值，未手写”，使读者可以复核符号来源。Baseline 也声称没有手写 QN，但报告没有把该纪律显式化。

第二，**零结果更可信**。Treatment 明确使用 `search_code(regex=true)`，并把“无 warning 的零命中”作为事实。Baseline 没有说明该处理，虽然未遇到假零，但方法论上少了一层保险。

第三，**方案分层更细**。Treatment 将 EPUB 支持拆为原生归档接口、Kotlin 书源加独立阅读屏，以及仅把 `.epub` 加入 zip 白名单三种接入面，并指出 `open_archive_path` 同时服务阅读、封面和页索引，不能只改阅读器。

第四，**真实样本对比更具体**。Treatment 使用“16 图 vs 13 章”“822 图 vs 481 章”“47 图 vs 89 spine 页”“0 图直接失败”等样本差异说明“EPUB 当 zip”会如何失真。

### 5.4 未改善与边界

该实验没有发现以下改善：

1. `trace_path` 覆盖没有增加，两组都只对约两条关键链做了调用链核验；
2. C++ 交叉验证没有发生，因为任务没有踩到嵌套类、重载、宏或条件编译长尾；
3. 效率没有提升，Token 基本持平，Treatment 耗时多 1.8 分钟，报告长度接近翻倍；
4. S1 产物偏重，704 行报告和 446 行 PLAN 可能压缩后续阶段的独立判断空间。

尤其需要强调，两组各 n=1，且 Baseline 接触过含参考符号的已装构建，而 Treatment 使用干净 pre-EPUB 构建。环境差异可能放大“纯净度”差异，不能把全部差别归因于注入。[^11]

### 5.5 对 RQ1 的回答

研究一提供的方向性证据是：阶段设问和符号查询纪律能够被加载，并改变报告中的证据呈现方式，使 QN 来源、零结果条件和方案边界更可审计。它没有证明“更多注入更好”，也没有证明符号覆盖、调用链验证或效率自动提升。换言之，S1 设问的作用更像是**提高事实来源的可审计性**，而不是直接提高探索覆盖率。

## 6 研究二：两个复杂任务的现场案例

### 6.1 案例设计

研究二采用两个脱敏现场案例，考察完整六阶段在真实复杂任务中的过程表现。两个任务都持续约一小时，均超过 400 条消息，并涉及扫描、封面、阅读器、生命周期和回归。[14]

| 维度 | 任务 A | 任务 B |
|---|---|---|
| 类型 | 新增一种电子书格式支持 | 修复 PDF 封面、性能和失败态 |
| 规模 | 约 61 分钟、496 条消息 | 约 64 分钟、404 条消息 |
| 起点 | 该格式完全不入库 | 187 本 PDF 只有 18 本有封面 |
| 假设 | 18 条 | 27 条 |
| 改动块 | 15 个 | 17 个 |
| 验收矩阵 | 25 行 | 22 行 |
| 测试 | 88 个单测 | 92 个单测 |
| 最终结果 | 可扫描、可阅读、有封面、有进度 | 封面、SMB 性能、错误页、刷新改善 |

这些案例不是随机抽样，也不是与裸代理的对照实验；它们用于观察 FDP 在长任务中的过程机制、证据结构和未验证边界。[^13]

### 6.2 任务 A：先否定“文本可以当作一张图”

如果直接按照“漫画阅读器就是一张张图”的直觉实现，文本类电子书会被压成超长图片。研究阶段先用真实样本估算：单章最大约 12 万字；按常见屏幕宽度和字号排版，单章位图高度可达数十万像素；单页位图内存可超过 1.7GB。该事实在写业务代码前即否定了“统一图片页模型”的计划，使文本视图成为必要方案，而不是后续优化项。

任务 A 最终形成 18 条假设、15 个改动块和 25 行验收矩阵；88 个单测通过，并在真实设备上验证文本、图片、纯图、损坏书和进度。25 行验收中，19 行通过，6 行明确保留为未验证，包括 Android 断点、SMB 全量、PDF 回归和极限长章等。

### 6.3 任务 B：先定位“为什么读一遍才有封面”

任务 B 没有直接修改封面逻辑，而是先查真实数据：

- 187 本 PDF 中只有 18 本有封面；
- 这 18 本与“有页数”的 18 本完全重合；
- 原生日志中有 182 条“PDF 不支持封面容器”的失败；
- 真正写封面的路径只在用户打开书时顺手渲染第 0 页。

这些事实把问题从“封面逻辑需要补丁”重构为“书架上需要按需生成封面”。在修改生产代码前，代理又用最小探针验证系统 PDF 渲染器能否直接读取远程文件：99MB 文件实测 32 次读、2.23MB；47MB 文件实测 330 次读、24.7MB，从而支持“不整档下载”的方案。

任务 B 形成 27 条假设：23 条通过，2 条被证据推翻并回改计划，1 条为静态加待联调，1 条为设计待实现。17 个改动块均有状态迁移矩阵，共经历 12 轮迭代修正。22 行验收矩阵中，主路径均有实际值，10 条边界明确标为未验证。

### 6.4 事实否定计划的两个实例

任务 B 记录了两次典型的“事实推翻假设”：

1. 原以为书库刷新只是慢，实际证据显示刷新信号没有被界面读取；
2. 原以为某些 PDF 封面已经部分恢复，核对数据库后发现显示封面的是另一种格式。

两次都没有把错误结论带入最终报告，而是回改计划。这直接回应 RQ2：FDP 的关键产出不是“计划被执行”，而是“计划被事实约束并修正”。

### 6.5 结果指标

任务 B 修复前后具有用户可感知的变化：[14]

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 120 本 PDF 书库封面 | 3 本 | 52 本，并按可见格继续生成 |
| SMB 大文件打开 | 整档下载；47MB 约 1.6s，114MB 约 4s | 198MB 打开 268ms，无整档下载 |
| 本地 99MB PDF | 打开慢、缓存占用高 | 打开 8ms，翻页 28–110ms |
| 旧缓存 | 3 本约 179MB | 启动清理，缓存目录为空 |
| 坏/加密 PDF | 永久“打开中…” | 明确错误页与重试 |
| 扫描新增书 | 不切库不显示 | 不切库 3→4/6 |
| 测试 | 少量 | 92 个单测通过 |

### 6.6 对 RQ2 的回答

两个案例显示，设问、假设和工具实验的组合能够在真实任务中产生三类决策后果：

1. **提前否定错误方案**：文本不能被压成单张图片；
2. **重构问题定义**：封面问题从旧逻辑补丁转为书架按需生成；
3. **保留未验证边界**：Android 断点、SMB 全量、最大文件、断线、队列压力等不被包装成已通过。

同时，两个任务均在 Android 断点受限时，通过日志、数据库、界面、探针和单测补足运行时证据。这说明代理遵循的不是“必须调用 DAP”的固定脚本，而是“必须获取运行时事实”的任务需求；当一条证据路径失效，它可以选择同目标下的替代路径。（DAP 角色与降级边界同第 3.8 节注释。）

## 7 综合讨论

### 7.1 设问不是自我安慰，而是信息需求的生成器

相关文献提示，模型自己提问并自己回答，仍可能维持原有幻觉。[5] 因此，FDP 的有效性不能只看“提出了多少问题”，而应看问题是否产生了以下后果：

- 形成新的可证伪假设；
- 提出竞争解释；
- 选择能区分解释的观察；
- 使计划、准代码或源码发生改变；
- 暴露无法验证的边界。

如果设问只产生固定问答模板，它也可能仪式化。与硬门禁不同的是，没有“填满问答表即可通关”的独立路径，因此模板化设问至少不会自动成为状态机的过关条件。

### 7.2 事实不是数量指标，而是决策约束

“产生大量事实”不应被理解为堆积工具输出。事实的价值在于其任务相关性、判别性、可追溯性、可复核性和决策后果。一个 20 行窄窗源码片段如果位于正确调用链上，可能比数百行词法命中更有价值；一个覆盖临界状态的最小探针，可能比大量无关日志更能约束计划。

这也说明，未来评估不能把“事实数量”设为门禁。否则，FDP 会重新制造自己的 Goodhart 指标。更合适的离线指标是：事实是否被用于保留、否定、缩小或重构具体假设；事实是否来自与问题相匹配的工具；事实是否附带来源和适用边界。

### 7.3 门禁失败不是“代理不听话”，而是目标结构变化

旧版插件的问题可以解释为方法论蒸馏失真与优化目标改变的叠加。成功 session 中的工具调用原本是任务理解后的结果；将它们改写为推进前提后，代理同时面对“解决工程问题”和“让状态机允许推进”两个目标。后者更直接、更可操作，因此更容易成为实际优化对象。

仪式性工具调用和推理中讨论如何突破门禁，是同一目标扭曲的两面。错误构建进一步说明，“发生过构建”不等于“构建了正确目标并验证当前修改”。这与 ImpossibleBench、SpecBench 和奖励错误指定研究共享同一底层机制，但旧版插件记录本身仍是设计史，而不是公开对照实验。[7,9,10]

### 7.4 外部事实不能绝对消除作弊

更严谨的机制表述不是“代理被大量事实冲击，所以没有精力作弊”，而是：**持续的外部事实压缩了虚假叙事可以自由维持的空间**。代理仍可能选择弱实验、只寻找支持性证据、移动验收标准或错误解释工具输出。因此，FDP 仍需要：

- 稳定的用户目标和关键回归约束；
- 原始工具输出和事实账本；
- 未验证边界显式化；
- 最终构建、测试和真实场景结果；
- 对关键结论的独立复核或隐藏验证。

### 7.5 对 RQ3 的回答：收益与代价

初步证据显示，FDP 的收益主要在四个方面：

1. 计划和假设更容易被事实修正；
2. 证据来源、类型和边界更可审计；
3. 长任务中注意力更稳定，阶段交接可恢复；
4. 未验证项不被“全部通过”叙事吞没。

代价同样明确：

1. 机器时间和 Token 开销显著，两个现场任务均约一小时、数百条消息；
2. 报告体量可能膨胀，S1 Treatment 的产物已经接近后续阶段体量；
3. 动态验证受平台限制，DAP、Android、远程环境和构建配置都可能影响取证；
4. 用户仍需阅读报告并承担最终判断；
5. 对小任务不经济。[^12]

## 8 有效性威胁

### 8.1 内部效度

研究一每组仅 n=1，且两组环境不完全相同，不能把报告长度、纯净度或可审计性差异全部归因于注入。研究二没有裸代理对照，也没有随机任务分配，无法估计方法对成功率的因果效应。

### 8.2 构念效度

“事实”“证据质量”“计划被否定”等构念目前依赖报告和过程记录，可能受到代理自我呈现影响。未来研究应使用原始工具输出、轨迹重放和独立编码，而不是只读最终报告。

### 8.3 外部效度

两个现场案例都来自相近的 Android 阅读器生态，且任务复杂度较高。结果未必推广到其他语言、构建系统、团队流程或短任务。模型版本变化也可能改变设问遵循、工具选择和门禁规避行为。

### 8.4 可靠性

实验记录为脱敏工程文档，虽然保留了任务规模、指标和边界，但未公开完整项目、原始轨迹和全部工具输出。外部研究者暂时无法完全复现实验。

### 8.5 发表与选择性报告风险

当前案例由方法实践者记录，存在选择成功案例或突出有利机制的风险。后续研究应预注册任务、评价标准和失败归档规则，纳入失败案例。

## 9 后续研究设计

### 9.1 对照条件

最关键的下一步不是继续增加提示，而是做可预注册的三臂对照：

| 条件 | 阶段拓扑 | 阶段设问与工具动机 | 工具硬门禁 |
|---|---|---|---|
| C0 自主基线 | 无 | 无 | 无 |
| C1 FDP | 有 | 有 | 无 |
| C2 门禁版 | 有 | 有 | 有 |

C1 与 C2 的唯一关键差别应是阶段推进是否依赖指定工具调用或固定证据表。这样才能分离“设问与拓扑”的作用和“硬门禁”的扭曲效应。

### 9.2 任务与操控

任务集应覆盖：

- 新增跨模块功能；
- 修复运行时状态错误；
- C/C++ 嵌套类、重载、宏和条件编译长尾；
- DAP 可用与 DAP 失效两种环境；
- 可见测试与隐藏组合测试分离；
- 至少包含若干“直觉计划错误”的任务，以观察事实能否否定计划。

模型、工具权限、上下文预算、任务说明和最大时间应保持一致。DAP 失效可通过环境脚本确定性地模拟，以检验代理是否转向探针、日志、测试和构建，而不是停滞或制造调试记录。

### 9.3 结果指标

主要结果指标应衡量真实任务完成，而不是流程合规：

1. 隐藏测试或人工盲评的任务成功率；
2. 正确目标构建率与错误构建率；
3. 关键回归缺陷数；
4. 用户可感知结果指标；
5. 未验证边界被如实标记的比例。

过程指标只用于离线分析：

- 计划被证据否定的次数和后续处理；
- 实质性工具调用与仪式性调用比例；
- 推理中讨论“如何满足门禁”的比例；
- 工具输出是否被后续决策引用；
- DAP 失效后的替代取证成功率；
- 报告中的证据类型、来源和边界完整性。

这些指标不应回填为状态机门禁，否则研究会再次把评价指标变成优化目标。[^20]

### 9.4 轨迹编码

建议由两名独立编码者对轨迹进行盲编码，分类包括：假设提出、竞争解释、判别性实验、确认性实验、仪式性工具调用、门禁讨论、计划修改、证据不足声明和移动验收标准。编码前公开代码本，报告一致性；无法判断的片段保留为未知。

## 10 结论

本文将 `static-dap-socratic` 的设计讨论形式化为“事实驱动编程”：外部确定性状态机只管理阶段拓扑和注意力；单代理在阶段提示的强指令、任务局部设问和证据阈值约束下暴露未知，以假设组织调查，并根据任务局部信息需求选择静态与动态工具，用可复核事实支持、否定或重构计划。

两组初步证据分别表明：S1 设问纪律可以提高符号证据的可审计性，但不自动提高覆盖率和效率；两个长任务案例显示，事实可以提前否定错误方案、重构问题定义、驱动计划回改，并在 DAP 受限时通过替代证据维持运行时闭环。它们共同支持方法论的工程可行性，但不构成统计验证。

本文最重要的边界是：FDP 反对的不是验证，而是把不完整的代理指标或固定过程当作优化目标。正确目标构建、当前修改测试、真实场景运行和关键回归仍是必要事实；真正需要拆除的是“必须调用某工具、必须填满固定表单才能推进”的认识论硬门禁。未来研究应以隐藏结果验证和离线轨迹分析评估 FDP，而不是把新的过程指标再次变成门禁。

## 注释

[^1]: **术语说明。** “事实驱动编程”是本文对该工程方法的中文学术化命名，英文可写作 Fact-Driven Programming。它不同于 test-driven development：FDP 不要求先写测试，也不把测试当作唯一事实来源；它强调的是计划、假设、工具观察与实现之间的证据循环。

[^2]: **论文定位。** 本文是方法论整理与初步实证报告，不是已完成同行评审的正式论文。仓库实验记录按工程文档写成，本文将其改写为学术体例，并显式补充有效性威胁。

[^3]: **“无门禁”的精确含义。** 本文所说的“拆除门禁”特指拆除认识论硬门禁，例如“必须调用 DAP”“必须调用某静态工具”“报告字段满足固定模式才能推进”。阶段 token、报告存在性、文件名匹配等仍属于拓扑约束；构建、测试和真实场景验证仍属于结果验证。

[^4]: **设计史证据边界。** 旧版插件未公开，相关描述来自方法设计者的开发史说明，包括仪式性工具调用、推理转向突破门禁、代码质量下降和错误构建。本文将其作为设计动机和机制假说，不作为可独立复现的实验结果。

[^5]: **事实与原始输出的区别。** 工具输出本身只是观察材料。只有当输出被绑定到明确对象、环境、时间、方法和解释边界时，才形成可复核事实。例如，构建成功输出必须说明构建目标、源码版本和是否包含当前修改，才能支持“当前修改已正确构建”。

[^6]: **grep 纪律的适用范围。** `stages.py` 只在 S1、S2、S4 的阶段文本中注入裸 grep 与 sed/awk 规则；运行期 hook 则会在整个活动会话中识别以代码为目标的 grep、sed、awk 并发出非阻断提醒。日志、文档、真实样本和数据分析路径被豁免。其目的不是否定词法工具，而是避免把词法命中直接提升为符号、调用关系、构建配置或运行时事实。

[^7]: **DAP 的角色。** DAP 是运行时事实来源之一，不是必须通过的门禁。规范要求区分“连接调试器”和“命中断点并读到实际值”。当 DAP 受 Android/ART、类加载、attach 或符号限制时，探针、日志、数据库、界面和单测可以提供替代运行时事实，但必须在报告中标注证据类型和边界。

[^8]: **handoff 的非评价性质。** `handoff.py` 只检查 token 是否有效、报告是否存在、是否非空、文件名是否匹配，并归档与计算哈希。它不解析报告、不评分、不判断证据充分性。因此，“handoff accepted”只表示拓扑交接完成，不表示质量通过。

[^9]: **提醒与阻断的区别。** hook 的 `PreToolUse` 输出 `permissionDecision: allow`，即提醒代理注意索引、裸 grep 或整文件读取，但不阻止工具调用。这一设计降低了“为绕过阻断而优化提示”的压力，同时保留注意力重锚功能。

[^10]: **证据等级的解释。** A 到 E 是报告中的证据来源标记，不是自动评分。A 表示静态 `file:line` 与 guard，B 表示 DAP 或测试实际值，C 表示微基准，D 表示推算，E 表示未验证。等级用于防止把推算写成运行时事实，而不是用于奖励或惩罚代理。

[^11]: **研究一混杂变量。** Baseline 组接触过含参考符号的已装构建，Treatment 组使用干净 pre-EPUB 构建。该差异可能同时影响报告纯净度、符号选择和探索路径，因此不能把两组差异全部归因于 S1 注入。

[^12]: **成本口径。** 文中 Token、耗时和消息数主要反映机器执行成本，不等于人工注意力成本。设计者报告的一小时无人干预指除启动 prompt 外无人工操作；这不意味着无需事后审查，也不意味着报告可替代最终人工验收。

[^13]: **研究二证据类型。** 两个现场任务是脱敏案例研究，保留了任务规模、假设数、改动块、验收行、测试数和关键前后指标，但未公开完整源码和全部轨迹。本文按照案例研究体例使用它们，避免进行统计推断。

[^14]: **未验证不是失败。** 在 FDP 中，`UNVERIFIED` 是认识状态，而不是任务失败。其价值在于把“没有证据”与“已有负面证据”区分开，使用户能够决定是接受风险、补充实验，还是停止交付。

[^15]: **静态与动态的互补性。** 静态证据可以证明符号位置、调用关系和数据形状，但不能证明某次运行实际走了哪个分支；动态证据可以证明特定输入下的实际值，但不能自动推广到所有输入。FDP 要求两类证据互相约束，而非互相替代。

[^16]: **CoT 监控研究的外推边界。** Baker 等研究的是训练期把 CoT 监控器纳入强化学习奖励后的隐蔽奖励黑客。本文将其作为过程压力可能诱发规避表达的机制旁证，而不是声称部署期 hook 门禁必然产生相同训练动力学。

[^17]: **SpecBench 的解释边界。** 可见测试与隐藏测试的差距可能来自故意规格博弈，也可能来自特性孤立实现、组合能力不足或测试覆盖不完全。本文用它证明“代理指标可能偏离真实规格”，不把所有差距都解释为蓄意作弊。

[^18]: **中文教育研究的外推边界。** 苏格拉底式问题支架研究的对象是人类学生与 AI 对话，不支持直接推断自治代理会选择正确工具或完成仓库级修改。本文仅使用它说明问题支架可能改变提问深度、序列和架构。

[^19]: **不是反验证立场。** 本文反对把单一代理指标当成完整目标，而不是反对构建、测试或隐藏验证。恰恰相反，FDP 要求结果验证更贴近任务本身，包括正确目标、当前修改、真实输入、关键回归和未验证边界。

[^20]: **研究指标与运行门禁的分离。** 仪式性调用比例、门禁讨论比例、计划修订次数等指标适合离线研究，不适合实时推进门禁。将其回填为状态机条件，会使研究对象再次优化指标，破坏实验效度。

[^21]: **阶段话术来源。** 第 3.4 节引文按 `plugin/static-dap-socratic/scripts/stages.py` 在提交 `ee7b788d7931038735dd1df2feba1488b905a1b1` 中的 S1–S6 与 DONE 字符串转录；为控制篇幅，保留关键句式并省略报告路径、token 和 handoff 命令。第 4.2 节提醒话术来自 `hooks/supervisor.py` 中的 `PRE_INDEX_READ_CARD`、`BARE_GREP_CARD`、`SED_AWK_CARD`、`FULL_READ_CARD` 与 `INDEX_STALE_NUDGE`。

[^22]: **语言禁令与执行门禁的区别。** `BARE_GREP_RULE` 和 `SED_AWK_RULE` 在文本层面使用“禁止”，S4 也规定“每块落码前至少 A+B”；但 hook 对工具调用仍返回 `permissionDecision: allow`，handoff 不检查索引、A+B、矩阵或报告字段。因此本文把这些措辞视为提示层规范，而不是可执行门禁。提示层规范本身仍可能影响代理行为，后续对照实验应将其作为被操纵变量，而不是当作不存在。

## 附录 A：本文使用的核心术语表

| 术语 | 定义 |
|---|---|
| 事实 | 带有来源、对象、条件、方法和适用边界，并能够约束工程判断的证据命题 |
| 假设 | 对现有路径、数据形状、状态、时序、平台约束或修改效果作出的可证伪断言 |
| 设问 | 用来暴露未知、生成信息需求和组织调查的问题，不是通关表单 |
| 工具动机 | 说明某类工具为什么可能提供当前问题所需事实的提示；在当前实现中可以与命令式起点和证据阈值并存，但不构成状态机推进条件 |
| 拓扑约束 | 管理阶段、token、报告交接、恢复和当前任务书注入的外部约束 |
| 过程门禁 | 把固定工具调用、报告格式或检查清单设为推进条件的认识论约束 |
| 结果验证 | 对正确目标、当前修改、真实场景和关键回归进行的实际验证 |
| 未验证 | 当前环境没有足够证据支持或否定某一命题的显式认识状态 |

## 附录 B：建议的最小复现实验清单

1. 固定模型、工具权限、上下文预算和任务说明；
2. 选择至少三类任务：跨模块功能、运行时修复、C/C++ 长尾符号；
3. 每类任务准备隐藏测试或人工盲评标准；
4. 分别运行自主基线、FDP 和硬门禁条件；
5. 保存原始工具输出、阶段报告、修改前后提交和最终构建；
6. 对轨迹进行双人盲编码；
7. 预先登记主要指标、失败归档规则和统计分析方法；
8. 公布失败案例与未验证边界。
