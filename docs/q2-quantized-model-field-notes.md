# 研究记录：量化小模型能否产生介入式因果轨迹（脱敏）

> 对象：一个本地 Q2 量化模型 + 事实驱动编程（FDP）的 S1/S2 流程。
> 已脱敏：不含凭据、主机/IP/共享名、设备标识、应用包名、个人书库书名、文件路径或可识别个人的数据；样本用“小/中/大 PDF”“52MB 样本”等代称。
> 结论只代表该本地环境与这批任务，不外推到其他模型/仓库。
> 方法论背景见 [事实驱动编程](fact-driven-programming.md)。

## 1. 研究问题

不是“模型能不能写代码”，而是：

1. 量化后的小模型能不能**自己发起前提审计/介入式因果推断**——在没有用户点名“缓存有问题”的情况下，自己问“这个机制该不该存在、没有它会怎样”？
2. 如果不能，外部提示词/拓扑/框架能不能把它逼出来？哪些部分有效：注意力拆分、工具纪律、账本/门禁、随机采样、验证器？
3. 为什么盲 grep/rg 在混合语言项目上会致命？什么样的工具政策能让它写出可编译的修改？
4. 这套工作流的稳定上限是什么：半自动、概率性轨迹收割，还是可以托付？

## 2. 背景

### 2.1 项目：一个“快”字长出来的混合语言阅读器

最初的漫画阅读器只做三件事：读 SMB 分享目录、读 zip、快。C++ 主干在 Windows 上写成，后移植到 Android 成为主干；UI 是 Kotlin/Compose，核心是 C++，中间隔着 JNI；构建同时依赖 Gradle 与 CMake/NDK；第三方库包括 SMB、解压、图像解码、SQLite、推理等。

复杂度不在“文件多”，而在**边界多**：

- Windows C++ 的路径/IO/线程/编码假设 → Android 的 VFS、文件描述符、scoped storage、JNI；
- Kotlin ↔ JNI ↔ C++ ABI 的对象所有权、线程、生命周期、异常语义；
- 双构建系统；
- 远端 SMB 读取、缓存、FD/会话；
- Compose 隐式调用、重组、生命周期；
- 第三方库的 ABI、编译开关、许可证。

更早的功能（翻译、标签数据库、动图、阅读模式、性能调优）是在 4.1 版模型 + 人工监督下用 FDP 一点点加上去的。**PDF/EPUB 那一版不是 FDP 产物**：代理自行考古过去成功的工作流，生成了一个插件，在质量门禁的监督下表演式地使用工具，把 PDF/EPUB 接进归档模型。因此它是 bolt-on，带着“归档假设”：统一容器入口、整文件 materialize、封面后置、页数打开才有。质量门禁保证了流程/报告的形状，但没有做架构前提审计；这解释了后来暴露的整库下载/缓存膨胀副作用。

这个项目是**分布外 stress test**：主流的 Python/单语言/定位类评测覆盖不到它；在这里，盲 grep/rg 不是低效，而是会直接编译失败。

### 2.2 模型：Q2 量化改了什么

被测模型是 DeepSeek-V4.1-Flash-1017 的 Q2 量化版本。量化 recipe 的特点是：

- 只量化 routed experts（gate/up 用低比特，down 用 Q2_K）；
- shared experts、attention/projections/output 保持较高精度（Q8/F16）；
- router 保持高精度；
- Engram 表基本 native。

因此它的**知识/选项生成**应接近官方版本；真正受损的是**选择、优先级、先验突破、持续执行**。对照的官方版本在同一任务、约 480k 上下文下仍能自己做 P0 proxy-FD；本地 Q2 在更低上下文没有做。上下文长度不是决定项，选择与执行才是。

## 3. 方法

- **S1**：读需求 → 索引/定向结构 → 现状路径/状态/失败模式 → 静态+动态研究方法论 → 写 `PLAN-v0`。目标是让 PLAN 自己暴露“被选 vs 替代”的分叉。
- **S2**：读 PLAN → A/B/C 三层假设（A 方案先验选择、B 动机/方案分叉、C 实现事实）→ 每条至少一个实验 → 拿实际值 → 判断是否重构 PLAN → 重写 PLAN → 报告/handoff。
- **节点**：每个 run 一个新 session；S1/S2 都用独立 session，不继承上一轮上下文。
- **证据**：静态结构工具（符号/调用图/字段/类型）定结构；DAP/DB/logcat/UI/最小 probe 定运行时；单样本只标“单点”，不冒充分布。
- **门禁**：报告/工件存在性、B 层杀死测量、未验证项单列；不把“构建成功”当“运行通过”。

## 4. 失败模式与提示词迭代

### 4.1 观察到的失败

| 阶段 | 失败 | 实际表现 |
|---|---|---|
| S1 早期 | 把“覆盖真实规模”执行成全库逐文件扫描 | 约 53 分钟、204k tokens，无 PLAN |
| S1 中期 | 要求先写方法论，模型转头读源码 | 约 10 分钟、85k，无 METHODOLOGY |
| S1 后期 | 方法论前置成功，但候选轴漏掉“移除持久状态” | 方法论 20.8KB；无 PLAN |
| S1 快速草稿 | 要求“立刻写、允许不完美”，模型仍持续 rg/read | 17 分钟无 PLAN；read/grep 绕过 |
| S1 运维 | `adb jdwp` 挂起 + 上一轮 pi 孤儿进程占单驻留模型槽 | 58 分钟无 PLAN |
| S2 旧版 | 长 session、账本滞后、B 层替代项都是下载策略 | 1h54m、395k；REPORT/PLAN 有，但整文件缓存保留 |
| 完整 S1–S6 | 产品可构建、可见需求基本完成 | 3h25m、250 调用、429k；但留下 3.6–4.1GB 整库下载缓存，真机存储打满 |

### 4.2 提示词调整：每一版修了什么

**S2 侧：**

- 早期用 L/S/B 先验分级 → 变成填表，实验围绕标签转；删除分级，改为“实验后才有权重”。
- 加入 A/B/C 三层：A 方案先验选择、B 动机分叉（被选/替代/判据/为什么胜/什么测量会让它输/若输改哪条）、C 实现事实。
- 加入“B 层必须 A/B，不能只测被选方案内部”；替代方案不可实现时，测决定优劣的关键量并写推断边界。
- 把“PLAN 得以实现所依赖的假设”改为“PLAN 所蕴含的假设”，避免与动机假设矛盾。
- 删除提示性例子，避免泄漏答案。
- 结果：旧版 S2 能写出报告/PLAN，但整文件缓存仍未被杀——B5 的被选与替代都是下载策略，缓存是共同底座，不是候选。

**S1 侧：**

- 需求先行，删除“问题一定在现有实现里”——这句话把现有实现提前放进被告席，是框架泄漏。
- 删除“先验检测/普世真理/反驳表”——对抗性过强，模型进入 compliance mode，CoT 变短。
- 加“不要用全量遍历代替采样设计”——全库扫描后的补丁。
- 禁盲 grep/rg/awk/sed；随后补 read 源码禁令——模型会用 read 绕过 grep 禁令。
- 明确“PLAN-v0 写完即停”，砍掉 REPORT/handoff，先把先验方案拿出来。
- 最终正式 S1 + 代码禁令 + 静态/动态方法论 + PLAN-v0：约 52 分钟、184 调用、262k，写出 30KB PLAN-v0。

### 4.3 盲 grep/rg 为什么致命

在混合语言项目里，grep 能找到 `PdfBookSource`，但找不到：

- JNI 注册/ABI 对齐、Kotlin ↔ C++ 的所有权/线程/生命周期；
- Gradle + CMake/NDK 的构建依赖；
- Compose 的隐式调用/重组；
- SMB VFS 的会话/FD/线程约束；
- 第三方库的编译开关/许可证。

基于文本片段的修改，调用者/被调用者、线程/锁、ABI 往往对不上，编译不过或运行即崩。禁令不是风格要求，是正确性要求；而且 prompt 禁令必须配外部 tool-call 检查，否则模型会换 `read` 绕过。

## 5. 注意力：为什么必须外置

### 5.1 观察

- 旧 S2 在十余次调用后，CoT 从“假设验证”滑到“核对设计”；随后用 7.16GB 事实去杀“UI 懒生产者”，不是杀缓存。
- S1 快速草稿要求“立刻写 PLAN-v0”，模型仍持续 rg/read 源码；探索欲压过承诺。
- S1 全库扫描是没有采样/代价边界的直接结果。
- 用户侧另一个 Q8 量化模型上，注入几条工具规范后 CoT 明显缩短、认知“卸载”给规则；与 Q2 的 compliance mode 同构。

### 5.2 注意力不是一个单一容量

至少四层：

1. 架构窗口：层数/头数/位置编码/训练过的 context length；
2. 训练分布决定的可用比例：长上下文、多约束跟踪、指令层级；
3. 执行控制：保持当前目标/未关闭约束、抗干扰、何时推理/何时服从；
4. 量化/运行时：权重精度、KV cache 精度、attention kernel。

Q2 的量化主要伤第 3 层：知识/选项生成仍在，执行控制/先验突破/持续维持严重削弱。所以它“能列出方案”，但“守不住循环”。

### 5.3 为什么 prompt 越加越容易失效

- 密集的“必须/禁止”会把模型推进 compliance mode：CoT 变短，认知卸载给规则；规则越多，注意力越花在“遵守形式”而不是“当前 claim”。
- 先验分级、门禁化会让 CoT 围着门禁转；删除分级、删除先验表，都是为了把注意力还给当前假设。
- prompt 能修“当前节点”的表达，修不了“跨节点状态/循环”；旧 S2 改了十余版，仍没杀缓存。

### 5.4 外置注意力的做法

- 拆节点：一个节点 = 一条可证伪 claim + 一个证据工件；>20 调用或 >2 claim 再拆。
- 单 item 注入：只给需求 + 当前 item + 相关事实/决定切片 + 前置工件路径 + 输出 schema + 预算；不给全历史。
- 账本/议程：事实、决定、未关闭项、依赖边；账本必须边做边回填，不能等结束。
- 硬预算/提交门：到点必须写工件/账本增量；外部检查器扫 tool call（禁用源码 grep/rg/awk/sed/read）。
- 随机采样 + 验证器：同一 item 多次采样，用编译/测试/DB/probe 筛掉“看起来像做了”的轨迹。
- 压缩是 fallback：成功轮在 366–395k 结束，未触发 450k 自动压缩；如果账本未回填，压缩摘要会丢掉关键实际值。

## 6. 一次成功的介入式轨迹

### 6.1 过程

- 1h54m、299 调用、366k tokens；无压缩。
- 先写 HYPOTHESES（A/B/C，B 层 14 条，C 层 40 条，实验计划 17 组），再做实验、回填、重写 PLAN。
- 工具：静态结构、DB/UI/logcat、DAP stack/eval、构建探针、清封面/慢网/锁竞争实验。

### 6.2 被实测推翻的先验

| 先验 | 实测 | 结果 |
|---|---|---|
| 先 Kotlin 封面、后 native | 124 本 PDF 中 119 本未缓存（96%）；Kotlin 路径必须整档下载；native 只读 page0 压缩对象+xref | 先 Kotlin FAIL；native 前置 |
| 未缓存可占位/手动 | 完整墙 143/165 缺封面；每个可见 cell 一次远端会话 | 可见-only 不足；持久队列+预取 |
| 页缓存/预取是性能主修 | 顺序 125–167ms；首次 5 页并发锁等待 373–693ms；回看 137–206ms | 页缓存不是主修；队列/当前页优先/native 先 |
| 清封面只清缩略图是次要 | 清后缩略图 0、DB 仍 26 key、UI 全占位、冷启动仍全占位 | 必修 |
| 原生引擎许可“直接兼容” | 许可组合需整体开源或商业授权 | license gate |

### 6.3 关键实际值

- 全库远程 PDF 7.5GB；119/124 未缓存。
- Kotlin 路径：1.3MB→207ms，52MB≈5s，慢块 1MB→8976ms。
- native：52MB 样本 page0 0.17MB+39KB xref，约 60ms；Android 渲染 page0 17ms；page count 1.46ms。
- 原生引擎构建成功，约 7.9MB 动态库；渲染 17–37ms，对比系统 PDF 渲染器 125–465ms。
- 缓存目录 8 文件 108MB，无自动淘汰；UI 还误标“RAR 本地缓存”。
- 封面墙 143/165 缺封面；清封面后 DB 26 key/UI 全占位。
- 后台翻译会话关闭后仍残留 1 个文件描述符；切分模式同一 raw 页被解码 2–3 次；首次 5 页并发锁等待 3 个 waiter、373–693ms。

### 6.4 PLAN 重写

1. **PDF 原生引擎 + 范围读主线**；系统 PDF 渲染器降 fallback。
2. **远端正向 PDF 打开不再整档 materialize**；page count/renders/cover 走原生。
3. **封面队列**：可见 + 前后一屏预取 + 持久队列；清封面/重生成复位。
4. **性能**：当前页优先队列 + 限并发 + 原生 context；页缓存后置；切分共享 raw 位图。
5. **缓存**：PDF 默认不再整档缓存；其他格式/显式离线整档走有界 LRU + 容量上限 + 按书清理。
6. **隐藏毛病**：job 关闭、删除清理、损坏 PDF 错误态、EPUB 早退。
7. **许可/构建 gate**：许可决策、项目内构建 spike、失败回退。

### 6.5 仍未验证

原生引擎许可、项目内构建集成、context 并发、视觉/裁剪/色彩回归、慢网/坏网、真机性能、全库 page0 字节分布、EPUB 原生范围读、删除书运行时清理。全部写成 gate，不写成结论。

## 7. 结论与可复用规则

1. **Q2 不是可靠的因果 agent，它是概率性的因果轨迹生成器。** 外部注意力管理 + 禁盲 grep + 账本/门禁 + 随机采样 + 验证器，把命中概率从“接近零”抬到“可收割”。
2. **知识/选项生成与执行控制要分开评估。** 能列出方案不等于能守住循环；量化损失主要在执行层。
3. **盲 grep/rg 在混合语言项目里是致命项**，不是低效项；禁令必须覆盖 read 源码，并配 tool-call 检查。
4. **单 session 长跑不可靠**；节点粒度 = 一条可证伪 claim + 一个证据工件；账本必须边做边回填。
5. **先验分级/门禁化会反噬注意力**；用“什么测量会让它输”替代标签，用未验证 gate 替代结论。
6. **产品成功 ≠ 设计成功**：能编译、能验收，但可能留下整库下载/缓存膨胀的副作用；必须在方案层审。
7. **强模型/人只放在 framing 与最终验收**；弱模型做节点执行 + 多次采样 + 验证。
8. **压缩是 fallback**；成功轮在 366–395k 结束，未触发 450k；不能靠压缩保状态。

## 8. 边界

- 只有一个完整的 S2 成功案例；成功率/复现率未测，不能给“稳定能力”结论。
- 450k 自动压缩后的行为未验证；摘要是否保留关键实际值未知。
- 原生引擎的许可、项目内构建、并发、视觉、慢网、真机、page0 分布、EPUB、删除清理均为 gate。
- 结论只代表该本地 Q2 环境与这类混合语言任务；不外推到其他模型/仓库。
